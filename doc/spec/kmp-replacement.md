# Calendar Alarm — KMP リプレイス仕様書

最終更新: 2026-10-06 / 版: v0.2 (ドラフト)

## 1. 目的・背景

Google Play の「Calendar Alarm Clock Reminder」(4LIMIT Sports GmbH 製、
`com.app_by_LZ.calendar_alarm_clock`) と同等の体験を持つカレンダー連動アラームアプリを、
Kotlin Multiplatform (KMP) で自前実装する。

中核となる価値は「**登録したカレンダーの予定に対し、通知ではなく"止めるまで鳴り続ける
アラーム"を確実に鳴らす**」こと。競合アプリのレビューで最大の不満は機能不足ではなく
「鳴るはずが鳴らない / 止められない」という鳴動信頼性の揺れであり、本アプリは
**鳴動信頼性を設計の第一目標**とする。

## 2. スコープ

### 対象

- Android 版 (Kotlin + Jetpack Compose) を第一リリースとする
- KMP 構成で作り、ロジック層を iOS と共有できる状態を維持する
- iOS 版は Android 安定後に SwiftUI + AlarmKit (iOS 26+) で追加する

### 対象外 (初期版)

- iOS 26 未満のサポート (通知 30 秒制限で中核体験を再現できないため)
- Web / Desktop
- 他者アプリとのデータ共有・書き込み (読み取り専用とする)
- AI 補助機能

### UI の切り分け

本仕様書は**ロジック・アラーム鳴動・データモデル・プラットフォーム設計**を対象とし、
画面の見た目・操作性の細部は UI 仕様として別ドキュメント (`doc/spec/ui-ux.md` または
追跡 issue) で決める。§4 の画面一覧は機能の存在を担保するための列挙であり、
配置・スタイルの確定デザインではない。ロジック層 (カレンダー読み込み・アラーム
展開・鳴動制御) は UI の決定に依存しない構造にする。

## 5. アーキテクチャ

### 5.1 モジュール構成

```
calendar-alarm/
├── shared/                    # KMP 共通層
│   └── src/
│       ├── commonMain/        # 全OS共通ロジック
│       ├── androidMain/       # Android 固有 (CalendarContract, AlarmManager 接続)
│       └── iosMain/           # iOS 固有 (EventKit / AlarmKit ブリッジ)  ※Phase 3
├── androidApp/                # Android アプリ (Compose UI + 鳴動エンジン)
└── iosApp/                    # iOS アプリ (SwiftUI)  ※Phase 3
```

**共有層 (commonMain) に置くもの** — バグの巣窟を一本化する目的:

- イベント→アラーム展開ロジック (オフセット適用・ミュート・例外日・繰り返し計算)
- 日時・タイムゾーン処理 (`kotlinx-datetime`)
- カレンダーモデル正規化 (各ソースのイベントを共通 `CalendarEvent` に落とす)
- 設定・ルール (カレンダー毎の既定値、音量、スヌーズ間隔)
- 天気クライアント + 場所→予報マッピング (Ktor)
- DB (Room KMP)・リポジトリ定義・ViewModel/UseCase

**OS 側に残すもの** — 薄いアダプタ層:

- Android: CalendarContract 読み取り、AlarmManager スケジュール、鳴動 FGS、
  オーディオ再生、通知、ウィジェット (Glance)、権限フロー
- iOS: EventKit 読み取り、AlarmKit 呼び出し (Swift shim)、WidgetKit

### 5.2 expect/actual 境界

```kotlin
// commonMain
interface AlarmScheduler {
    suspend fun schedule(instances: List<AlarmInstance>)
    suspend fun cancel(ids: List<AlarmId>)
}
interface CalendarProvider {
    suspend fun calendars(): List<CalendarSource>
    suspend fun events(range: DateRange): List<CalendarEvent>
}
interface AlarmAudio { fun play(sound: AlarmSound); fun stop() }
```

| 境界 | Android actual | iOS actual |
|------|---------------|------------|
| AlarmScheduler | AlarmManager (`setAlarmClock`/`setExactAndAllowWhileIdle`) | AlarmKit (Swift shim 経由、ワンショット展開) |
| CalendarProvider | CalendarContract | EventKit |
| AlarmAudio | MediaPlayer (STREAM_ALARM) + FGS | AlarmKit の AlertSound (バンドル MP3) |
| 鳴動画面 | Full-screen Intent Activity | AlarmKit システム描画 (アプリ側 UI なし) |
| ウィジェット | Glance | WidgetKit |

### 5.3 アラーム展開アルゴリズム (共通層の核心)

1. 有効カレンダーのイベント + アラームルール → 鳴動すべき `AlarmInstance` を
   **展開ウィンドウ (既定 14 日先まで)** 分だけ計算する
2. 例外日・ミュート・オフセット・タイムゾーンを適用して確定時刻リストを生成
3. `AlarmScheduler` に差分適用 (追加/更新/削除のみ)
4. 再展開トリガ: カレンダー内容の変更検知・設定変更・端末再起動・
   タイムゾーン/ロケール変更・日付ロールオーバー

iOS は AlarmKit の予約上限 (約 64 件) と繰り返しが週次のみという制約があるため、
上記と同じ展開結果を「ワンショットの列」としてウィンドウ内に絞って予約する設計に揃える。

## 6. プラットフォーム設計 (Android)

### 鳴動経路

- `AlarmManager.setAlarmClock()` (最優先・設定アイコン表示) または
  `setExactAndAllowWhileIdle()` で時刻登録
- 発火時に `mediaPlayback` フォアグラウンドサービス起動 → STREAM_ALARM で
  カスタム音をループ再生 + フルスクリーン Intent で鳴動画面表示 + バイブ
- 停止/スヌーズは鳴動画面のボタン → サービス停止。スヌーズは次回発火を再登録
- `BOOT_COMPLETED` / `TIMEZONE_CHANGED` / `DATE_CHANGED` レシーバで再展開・再登録
- WorkManager でカレンダー差分同期と「鳴動予定の健全性チェック」を定期実行

### 権限・ポリシー

| 権限 | 用途 | 備考 |
|------|------|------|
| READ_CALENDAR | カレンダー読み込み | 実行時 |
| POST_NOTIFICATIONS | 鳴動通知/事前通知 | Android 13+ |
| USE_EXACT_ALARM | 正確なアラーム | アラーム中核アプリのため審査上許容 |
| USE_FULL_SCREEN_INTENT | 鳴動画面 | Android 14+ は設定画面誘導あり |
| FOREGROUND_SERVICE(_MEDIA_PLAYBACK/_DATA_SYNC) | 鳴動/同期 | |
| RECEIVE_BOOT_COMPLETED | 再起動後の再登録 | |
| VIBRATE / INTERNET | バイブ / 天気 | |
| ACCESS_*_LOCATION (任意) | 現在地ベースの天気 | 未許可でも場所文字列ジオコーディングで代替 |

### OEM 電池最適化対策

- 初回起動と設定画面から電池最適化除外のリクエスト導線を用意
  (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` は審査注意。基本は
  `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` へ誘導)
- Samsung / Xiaomi / OPPO 等のメーカー別設定手順をアプリ内ガイド化
- 「鳴らなかった」自己診断画面 (最後の鳴動・次回予定・権限状態を一覧)

### iOS (Phase 3) の要点

- **AlarmKit (iOS 26+)**: マナー/集中モード突破・停止まで鳴動・カスタム MP3
  (バンドル or `Library/Sounds` の AlertSound)。アラート UI はシステム描画
- 制約: 繰り返しは週次のみ・予約上限約 64 件・要 `NSAlarmKitUsageDescription` +
  `requestAuthorization`・countdown 表示に widget extension 必須
- 上限制約は「展開ウィンドウ内のワンショット列」を予約し、発火・編集の都度
  ローテーションする方式で回避
- Swift 専用 API のため KMP からは薄い Swift shim を介して呼ぶ
- アプリが見ていない間に鳴って止められたアラームは、AlarmKit の停止ボタンに付けた intent (`AlarmStopIntent`) が書き残した行を停止済みにする。書き残しが無くても、予約を入れた時 (`ScheduledRecord.reservedAtMillis`) から端末が起動し続けていて (`kern.boottime` がそれ以前)、鳴る時刻を過ぎ、AlarmKit から予約だけ消えている行は、鳴って止められたと見なして停止済みにする (`via=boot`)。予約のあとに再起動した行、予約した時刻が不明な旧版の行、起動時刻が読めない時は見なさず、書き残しの無い行は予約喪失として拾い直す (#61, #118, `OffAppStopPlan.swift`)
  - 既知の残り: この書き残しは intent が走った時だけ付く。Apple Developer Forums の報告 (https://developer.apple.com/forums/thread/815064, iOS 26.2.1, 2026-10-22 参照) では、ロック画面の停止ボタンでは intent が走る一方、画面を開いている時に鳴って画面操作で止めた場合と、バナーを上にスワイプして止めた場合は走らない (電源ボタンは未確認)。その経路でも書き残しは付かないが、起動し続けた端末なら上の `via=boot` の見なしで止めた扱いになる。残る穴は、端末が起動したまま OS が予約を黙って捨てた行も止めた扱いになり、鳴らず見逃し通知も出ないこと。残りの扱いは #130 で追う
- 通知アラーム（他アプリの通知で鳴らす）は iOS では出さない (#103)。他アプリの通知を読む公開 API が無い。出典は `doc/spec/parity-audit.md` の末尾

## 7. 信頼性設計 (差別化の中核)

競合の弱点 = 鳴動の不確実性。以下を仕様として担保する。

- **鳴動の二重経路**: AlarmManager 登録に加え、WorkManager が「次回鳴動が
  正しく登録されているか」を定期検査し、欠落を修復
- **監査ログ**: 「登録/発火/停止/スヌーズ/スキップ理由」を永続化し、
  設定画面の自己診断から参照可能にする (サポートのための説明責任)
- **同時刻衝突ポリシー**: 複数のアラームが重なった場合、後から鳴った方が画面と音を取り、
  鳴っていた方は止められていないので鳴動待ちに戻る。鳴っている方を止める (停止・スヌーズ・
  鳴動上限での自動停止) と、待っている方を直後に鳴らし直す。待ちが複数あれば同じ規則で
  1件ずつ鳴る (取りこぼさない)。順序の詳細:
  - 鳴らすかどうか (止め済み・猶予超過・ロック解除まで留保) は画面と音を取る前に決める。
    鳴らない後発が、鳴っている先行を黙らせない
  - 押し出された方は墓標を立てず、DB の行は FIRED (鳴ったが片付いていない) のまま待ち行列に載せる。
    PENDING に戻すと、resync が過去分を予約し直して後発の鳴動中に発火させてしまう。
    待ち行列は端末に保存するので、途中でプロセスが死んでも後発の停止後に鳴らし直す
  - 鳴らし直しは鳴動中の鳴動が無い時だけ、AlarmManager に今の時刻で入れ直して行う。
    同じアラームの START が重なっても鳴らし直さない (二重に鳴らない)
  - 待っている間に鳴動猶予 (60分) を過ぎた方は見逃しとして記録・通知する
- **鳴動中の状態永続化**: 鳴動画面を開かず再起動しても、未解決アラームは
  再鳴動する (レビューで「開くだけで消えた」系の苦情があった競合の轍を踏まない)
- **サイレント/マナー時の挙動**: STREAM_ALARM で鳴る仕様とし、
  音量 0 の場合はバイブ + 画面のみ (仕様として明文化)

## 7.1 予定の種類と「予定なし」の鳴動設定 (#79)

設定の一か所で、種類ごとと「予定なし」の予定を鳴らす・鳴らさないに切り替える。

| 種類 | 既定 | 理由 |
|---|---|---|
| 予定 | 鳴らす | このアプリの中心の価値 |
| タスク | 鳴らす | 時刻付きのタスクは、その時にやる意思 |
| 不在 | 鳴らさない | 応じない時間の印。知らせることが無い |
| サイレントモード | 鳴らさない | 邪魔されないために押さえた時間 |
| 勤務場所 | 鳴らさない | 毎日の終日の目印。鳴ると毎朝鳴る |
| 誕生日 | 鳴らさない | 終日・毎年。時刻に意味が無い |
| 予定なし (free) | 鳴らす | 黙って鳴らなくなるのが最悪の失敗 (§1) |

- 判定の順番: 予定一つへの個別指定 → 招待 → 種類 → 予定あり／なし。個別に「アラーム」を選んだ予定は必ず鳴る
- 仮 (tentative) と、空き状況が取れない予定は「予定あり」として扱う
- 予約の展開と予定一覧の表示は同じ判定関数 (`AlarmExpander.passesEventFilters`、iOS は同じ規則の写し) を使う
- 種類を OS が教えてくれるのは、Android の Google 連携時 (Calendar API の eventType) と、iOS の誕生日カレンダーだけ。
  それ以外はタイトルからの推定で、設定画面にもそう書く
- タイトルからの推定 (#306): 終日の予定は題に語を含めば分類する (誕生日・勤務場所は終日の予定のため)。
  **時刻のある予定は、題全体が語と一致する時だけ分類する**。題の前後の空白を除き、大文字小文字と全角・半角の違い、
  空白の連なりを揃えてから、語と完全に等しいかを見る。「出社して面談」「有休申請の締切」「Microsoft Office 研修」は
  普通の予定として鳴り、「不在」「在宅」だけの時刻付きの予定は分類されて鳴らない。
  オフィス・自宅・在宅は終日でも時刻付きでも題全体の一致だけで勤務場所にする (部分一致しない)。
  ooo (Out of office の略) も題全体の一致だけで不在にする。
  半角カナは正規化しない。
  Google の eventType が取れていればそれが先 (推定は使わない)。
  iOS は #307 まで部分一致のまま (Swift 側の写しは別)。
- 前から使っている人: Android は旧キー (`event_type_mask`) があれば選択を保つ。サイレントモードは「予定」と同じ値、予定なしは鳴らす。
  iOS は旧版の既定 (全部オン) のままなら一度も触っていないとみなして新しい既定値、変えていればその選択を保つ

## 7.3 終日予定の鳴動 (#144)

競合の「Calendar → All-day events」（取込トグル＋鳴動時刻、既定 10:00 AM）に対応。

- 取り込み ON/OFF と鳴動時刻はカレンダーごとのルール (`AlarmRule.allDayMinutes`) で持つ。
  既定 540 (9:00) = 鳴らす。負数 = そのカレンダーの終日予定を鳴らさない
- 鳴動時刻は「その予定日のローカル時刻」。終日予定の startMillis は UTC 0 時なので、
  タイムゾーンまたぎの日付境界は**端末ローカル日付**に倒す (`AlarmExpander` が UTC 日付を
  ローカルの allDayMinutes に解釈し直す)
- **複数日にまたがる終日予定は開始日だけ鳴らす**。Google の終日予定は end が翌日 0 時
  (排他) で、3日間の予定も「開始日の終日」として展開する。毎日鳴らすと誕生日や
  勤務場所の連続予定で毎朝鳴ってしまうため、繰り返し扱いにはしない

## 7.4 全イベント共通の追加リマインダー (#143)

競合の「Default Alarms」（全イベントに日:時:分の追加リマインダーを足す）に対応。2026-11-14 時点のコードの動きを書く。

- 設定は「開始の何分前か」の分数リスト。Android は `SettingsRepository.extraReminderOffsets`、iOS は `Store.extraReminderOffsets`。
  どちらも展開に `commonExtraOffsets` として渡す (`SharedBridge.ExpandRequest.commonExtraOffsets`、`AlarmRepository.kt:851`、`Engine.swift:314`)
- 入力は 0〜30 日・0〜23 時間・0〜59 分で、合計 0 分は不可。同じ値は追加できない (`SettingsScreen.kt:1875,1910-1913`)。
  設定画面でできるのは追加と削除 (チップのタップ)。登録済みの値をその場で書き換える操作は無く、直すときは消して足し直す
- **予定に効く追加リマインダー** (`AlarmExpander.effectiveExtraOffsets`, `AlarmExpander.kt:360-361`):
  - 予定ごとの追加リマインダーの指定がある予定は、その指定だけが効く。カレンダー既定も共通も効かない (空の指定は「追加なし」)
  - 指定が無い予定は、カレンダー既定の追加リマインダーと共通の追加リマインダーを足し合わせ、同じ値を1つにして使う
  - 予定の詳細シートは、今効いている値 (共通込み) を選択済みで出す。チップを触った時だけ、その一覧全体を予定ごとの指定として書く。
    時刻や動作だけ変えた時は書かない (`AgendaScreen.kt:643-648`)。一度書くと、その予定には後から共通を変えても届かない
- **同じ時刻の鳴動は1回だけ** (`AlarmExpander.kt:95-117`)。重複の判定は「分数」ではなく鳴動時刻 (`triggerAtMillis`) で、
  1つの予定の中で次の順に出し、先に出たものが勝つ。後から出た同時刻のものは捨てる:
  1. 開始のオフセット (予定ごとの指定、無ければカレンダーの何分前)。動作は「開始の動作」
  2. 追加リマインダー (カレンダー既定 + 共通を足したもの、または予定ごとの指定)。小さい分数から。動作は「リマインダーの動作」
  3. 予定側 (カレンダーに入っている通知) のリマインダー。「予定側の通知を取り込む」が ON の時だけ。負の値は捨てる
  - つまり、予定側の通知と同じ時刻に共通リマインダーがあっても鳴るのは1回。開始と同じ時刻なら開始の動作で1回。
    予定ごとの指定を持つ予定でも、予定側の通知の取り込みは止まらない (置き換わるのは1の次の追加リマインダーだけ)
  - 先に出す側の動作が「鳴らさない」の時と、一括ミュートで「アラーム」が抑えられる時は、時刻の席を取らずに戻る。
    そのため同じ時刻の後ろ側が代わりに出る (開始が「鳴らさない」でも、同時刻のリマインダーは鳴る)
  - 鳴動の id は勝った側の分数で付く (`ev:<予定>:b<分>`)
- 終日予定にも効く。鳴動時刻は「終日の鳴動時刻 (`allDayMinutes`、§7.3) から何分前」(`AlarmExpander.kt:82-92`)
- 予約するのは従来どおり鳴動時刻が 14 日以内のものだけ。開始が 14 日より先でも、共通リマインダーの分だけ前に出て 14 日以内に入るなら予約する。
  そのため予定の取得は、設定で分かっている最大の何分前だけ先へ延ばす (`fetchLeadMinutes`, `AlarmRepository.kt:797-806`)。
  予定側の通知を取り込む時は、読むまで分からないので上限 4 週 (`MAX_EVENT_REMINDER_MINUTES`) を使う
- 単発・曜日繰り返しのアラームとタイマーには共通リマインダーは効かない (`expandEvents` だけが使う)

## 7.5 放置したら自動でスヌーズ (#145)

競合の Auto-snooze に対応。**Android のみ**。iOS は AlarmKit のスヌーズボタンの範囲で、放置時の動きは OS 管轄のため対象外 (PR #186)。
2026-11-14 時点のコードの動き:

- 設定は 2 つ (`SettingsRepository.kt:108-114,291-295`、画面は `SettingsScreen.kt:1379-1402`)
  - 「放置したら自動でスヌーズ」: 既定 OFF。OFF の時は従来どおり、鳴動の上限時間に達したら「見逃し」にする
  - 「自動スヌーズの回数上限」: 2 / 3 / 4 回、既定 3。自動スヌーズが ON の時だけ画面に出る
- 設定は鳴動の始まりに写しを取り、その鳴動の間はその写しを使う (`AlarmService.kt:235,372-373`)。鳴動中に設定を変えても、鳴っている回には効かない
- 動き (`AlarmService.kt:374-421`): 鳴動の上限時間 (§7.6 の鳴動持続時間、制限なしなら 10 分) に達して自動停止した時、
  - 自動スヌーズが ON で、その鳴動の `snoozeSeq` が回数上限より小さければ、スヌーズ分数後に鳴り直す予約を作る。
    分数は、その鳴動に付いているスヌーズ分数、無ければ設定の既定スヌーズ分数 (`AlarmService.kt:394-396`)
  - そうでなければ「見逃し」にする: 状態を `MISSED` にし、見逃し通知を出す (`MissedNotifier.post`、`AlarmService.kt:409-421`)
- **「Alarm missed」相当の扱い**: 見逃し (`MISSED` + 見逃し通知) になるのは、連鎖の最後の鳴動が上限時間に達して、
  自動スヌーズが OFF か回数上限に届いている時の 1 回だけ。途中で自動スヌーズに置き換わった鳴動は `SNOOZED` で、見逃しに数えず通知も出さない
- **回数の数え方**: スヌーズは何であれ `snoozeSeq` を 1 つ進める (`Models.kt:294-296`)。連鎖は子の id が `<元の id>:snz1`, `:snz2`… と伸びる。
  数えるのは自動と手動の合計で、手動スヌーズも回数上限を使う
  - 例: 上限 3・手動スヌーズなしなら、鳴る → 放置 → 自動 1 回目 → 放置 → 自動 2 回目 → 放置 → 自動 3 回目 → 放置 → 見逃し。鳴動は計 4 回
  - 例: 上限 3 で 1 回手動スヌーズしたあと放置し続けると、自動スヌーズは 2 回で、3 回目の放置が見逃し
- スヌーズの予約は置き換えで、積み上げない (`snoozeRow`、`AlarmRepository.kt:589-`。元の行を `SNOOZED` にして子を 1 つだけ作る)
- 停止との競合は停止が勝つ。先に停止していれば子を作らない。自動スヌーズの子を作ってから 30 秒以内に停止が届いたら、その子も一緒に取り消す
  (`AlarmRepository.kt:388-397,552-565,1252`)
- コード上、アラームの種類による除外は無い。鳴動サービスで鳴る鳴動は同じ扱い (種類ごとの実機確認は未確認)

## 7.6 音量・「徐々に大きく」・鳴動持続時間 (#148)

**Android のみ**。iOS は AlarmKit に音量・徐々に大きく・鳴動持続時間の指定が無く、OS 管轄のため対象外 (`parity-audit.md` F-4、G1)。
2026-11-14 時点のコードの動き:

- **音量** (`AlarmService.kt:591-608`、`SettingsScreen.kt:1248-1260`、`SettingsRepository.kt:100-101`)
  - 設定は 0〜100 のスライダー。**0 = 端末のアラーム音量に従う** (画面は「音量: 端末設定」)。既定 0。「端末に従う」の別スイッチは無く、0 がそれ
  - 1〜100 は、鳴動の `MediaPlayer` に `setVolume(値/100)` を掛ける (STREAM_ALARM の音量に対する係数。端末側のアラーム音量が 0 なら無音は変わらない（未確認）)
  - §7 の「音量 0 はバイブ + 画面のみ」は端末のアラーム音量が 0 の場合の話で、アプリの音量 0 は「端末に従う」であって無音ではない
- **徐々に大きく (緩上昇) と 30 秒のクレッシェンドは同じもの** (1 つのスイッチ「音量を徐々に上げる」、`volumeCrescendo`、既定 OFF。`SettingsRepository.kt:103,180`、`SettingsScreen.kt:1318-1325`)
  - 時間の長さの設定は無く、30 秒固定 (`CRESCENDO_MS`、`AlarmService.kt:919`)。ほぼ無音 (0.05) から始め、20 段階 (1.5 秒ごと) で
    直線的に設定の音量まで上げる。最後の段で設定の音量に届く (`AlarmService.kt:645-655,920`)
  - **アプリの音量が 1〜100 の時だけ効く**。音量が 0 (端末に従う) の時は音量に触らないので、スイッチが ON でも最初から端末の音量で鳴る (`AlarmService.kt:607,621`)
  - 鳴動のたびに最初からやり直す。スヌーズの鳴り直しでも、また小さな音から始まる。停止・時間切れで止める (`AlarmService.kt:857-862`)
- **鳴動持続時間** (`AlarmService.kt:374-381,899`、`SettingsScreen.kt:1349-1365`、`SettingsRepository.kt:108`)
  - 選択肢は 5秒 / 10秒 / 30秒 / 1分 / 2分 / 5分 / 制限なし。既定は制限なし
  - 時間が来たら鳴動を自動停止し、自動スヌーズ (§7.5) か見逃しにする
  - **制限なしは本当に無制限ではなく、従来の 10 分の安全上限のまま** (通知権限なしで全画面表示も拒否した構成だと停止の画面が無く、電源が切れるまで鳴り続けるため。PR #185)
  - 30 秒より短い持続時間 (5・10 秒) では、クレッシェンドが設定の音量に届く前に止まる。クレッシェンドの長さは持続時間に合わせて縮まない

## 9. 非機能要件

- **オフライン**: カレンダー・アラーム・設定は完全オフライン動作 (天気のみ通信)
- **起動・軽量性**: 鳴動発火時の起き上がりが速いこと (Flutter エンジン等を
  積まない KMP/Android ネイティブであることの強みを活かす)
- **省電力**: 常駐ポーリングなし。WorkManager の最小頻度運用
- **ローカライズ**: 日本語・英語

## 9.5 UX 改善の方向性

競合レビューの不満 (鳴らない・止められない・設定が難しい) を踏まえた改善の**方向性**
を示す。最終デザインではなく、UI 仕様書が具体化する際の評価軸とする。

- イベントへのワンタップでアラーム設定 (一覧の行タップ → 既定オフセットで即 ON)
- 鳴動画面は「止める」「スヌーズ」を大きく・迷わせない構成にする
- 自己診断画面: 権限・電池最適化・通知ポリシーの状態を一覧化し、鳴らない原因を
  ユーザー自身が切り分けられるようにする (§7 と連動)
- 権限のオンボーディングを段階化 (最初に全部求めず、必要な時点で理由と共に求める)
- 設定項目を絞り、初期値がそのまま動く構成にする

## 9.6 完全リプレイスの判断

**結論: Android 版は完全リプレイスで問題ない。** iOS 版と既存ユーザーの移行は
個別の決定が要るため §12 に残す。

根拠:

- ストア説明の機能は F-1〜F-10 で概ねカバーする。カレンダー読み込み・イベント連動
  アラーム・フルスクリーン鳴動・スヌーズ・繰り返し・天気・タイマー・ウィジェットは
  全部仕様に入っており、差分はない
- 中核体験の「止めるまで鳴り続ける」は F-4/§11 のマトリクスで保証対象とし、
  信頼性では上回る設計にしている
- Android 先行なら AlarmKit (iOS 26+) の制約に引っ張られず、機能同等を先に出せる

リスクと軽減:

| リスク | 内容 | 軽減 |
|--------|------|------|
| OEM 電池最適化 | Xiaomi/OPPO 等の独自省電力でアラームが殺される | §6 OEM 電池最適化対策 + 自己診断画面で検出・誘導 |
| AlarmKit (iOS 26+) | iOS 版が OS 依存で Android と同じ鳴動を再現できない可能性 | Phase 3 で実機検証し、不可なら iOS 提供機能の範囲を再定義 |
| 既存ユーザーの移行 | 別アプリとして出す場合、登録済みアラーム・課金権限をどう引き継ぐか | §12 に残す (同一 app id 更新か別インストールかの決定) |
| Pro 課金の引き継ぎ | 既存購入者のエンタイトルメント | 課金 SDK 決定と合わせて §12 に残す |

## 11. 受け入れ条件 — 鳴動テストマトリクス

以下の全ケースで「指定時刻にフルスクリーン+音が鳴り、停止/スヌーズできる」こと。

| # | 状態 | 期待 |
|---|------|------|
| 1 | アプリ起動中 | 鳴動 |
| 2 | アプリ kill 後 | 鳴動 |
| 3 | 画面ロック中 | フルスクリーンで鳴動 |
| 4 | 端末再起動直後 (再ログイン前) | 鳴動 |
| 5 | マナー/サイレントモード | 鳴動 (STREAM_ALARM) |
| 6 | おやすみモード (DND) | 鳴動 |
| 7 | タイムゾーン変更後 | 正しい時刻に鳴動 |
| 8 | DST 境界 | 正しい時刻に鳴動 |
| 9 | 同時刻イベント複数 | 全件取りこぼしなく順次鳴動 |
| 10 | 例外日 | 鳴らない |
| 11 | ミュートカレンダー/イベント | 鳴らない |
| 12 | 電池最適化 ON のまま (未除外) | 鳴動 (setAlarmClock 経路) |
